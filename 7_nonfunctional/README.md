> 对象：`/home/donghe/github/opencode`（v2.0.30，`dev` 分支）。

## 一、为什么需要这一卷：非功能代码占大头是常态，不是问题

**正常路径只有一条，异常路径有无数条**——输入非法、网络超时、磁盘满、并发竞争、进程崩溃……每条都要处理。业界共识（Robert C. Martin 等）：核心业务逻辑往往只占 20%-40%，其余是"让系统在真实世界可靠运行"的代码。

**opencode 实测印证**（2026-10-22，find/wc 实测）：

| 实证 | 数字 | 含义 |
|---|---|---|
| 生产代码 | 15.0 万行（ts/tsx 非 test） | 分母 |
| 测试代码 | **27.6 万行**（1064 个测试文件） | 测试:生产 ≈ **1.8:1** |
| `shell/scan.ts` | **2409 行**，功能代码 0 行 | 一个"恐惧"（危险命令）长出一整个纯防御文件 |
| 恢复/重试/协调独立文件 | restart 240 + retry 115 + run-coordinator 196 + … | 还没算 bus.ts 908 行里的事务与锁 |
| `step.ts` / `tool/runtime.ts` | 321 行含 17 处防御 / 281 行含 29 处 | "一次 LLM 调用"的主体是防御，不是调用 |

这不是浪费——是**软件在真实世界生存的免疫系统**。读代码时感觉"复杂"，多半是撞上了这些恐惧的名字；把它们列成清单读完，仓库就不吓人了。

## 四、判断"过度防御"的四条标准（本卷的评估框架）

吸收业界共识，作为阅读每篇机制时的验收视角：

1. ✅ **合理的多**：每个异常分支有实际触发场景、有恢复策略、有日志
2. ❌ **过度**：为"永远不会发生"写复杂处理，而非快速失败（fail fast）
3. ❌ **过度**：重复防御代码本应抽为公共工具（对照 opencode：runtime.ts 的 foreign failure 强转正是"抽到边界一处"的正面示范）
4. ❌ **过度**：日志/埋点拖慢关键路径（对照：事件批量 10ms/100ms 正是为此）

**警示信号**：异常分支没测试覆盖（白写）、错误被吞（`catch(e){}` 比不写更危险）、正常流程被异常逻辑淹没（该重构）。
