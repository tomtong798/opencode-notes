## 0. Effect 解决什么问题

Go 里写一个"读配置 → 查库 → 调 LLM"的函数：

```go
func Process(ctx context.Context) (string, error) {
    cfg, err := loadConfig()          // 1. 可能出错
    if err != nil { return "", err }
    user, err := db.Query(ctx, cfg)   // 2. 可能出错，且依赖 ctx
    if err != nil { return "", err }
    resp, err := llm.Call(ctx, user)  // 3. 可能出错，且依赖 ctx
    if err != nil { return "", err }
    return resp.Text, nil
}
```

三个痛点，Effect 各有解法：

| Go 的痛点 | Effect 的解法 | 机制 |
|---|---|---|
| **错误处理啰嗦**：每个 `if err != nil` 手写，漏了编译器不管 | 错误类型进**类型签名**（`E`），签名上"撒谎"才报错 | 编译期类型检查 |
| **依赖隐式**：`ctx` 里有什么编译期不知道，`ctx.Value` 返回 `any` | 依赖进**类型签名**（`R`），缺依赖编译不过 | 编译期类型检查 |
| **副作用立即执行**：无法"先描述、再执行、可并发、可取消" | 计算是**惰性值**，组合后再执行 | 数据结构设计（非编译期） |

一个精确化：前两条是真·编译期检查；第三条不是编译器抓的，而是 Effect 作为惰性数据结构的运行时性质——构造 `Effect` 只是建对象，`runPromise`/`runFork` 才触发。

> **一句话**：Go 靠"约定和纪律"保证的事（错误不漏、依赖明确、副作用可控），Effect 全部上移到类型系统。抽象的泛型签名是代价，编译器检查是回报。

## 1. 核心基石：`Effect<A, E, R>` 三泛型

一段计算不是直接执行，而是先描述成值：

| 泛型 | 含义 | Go 类比 |
|---|---|---|
| `A` | **成功值**类型 | 返回值 |
| `E` | **失败**类型（具体类型，不是万能接口） | `error`，但是精确的 |
| `R` | **依赖**（需要哪些服务） | `ctx` 里需要的东西 |

现码示例——`pty.ts` 的服务接口，每个方法都是 Effect 签名：

```ts
// packages/core/src/pty.ts
export interface Interface {
  readonly get: (id: PtyID) => Effect.Effect<Info, NotFoundError>
  readonly remove: (id: PtyID) => Effect.Effect<void, NotFoundError>
  // ...
}
```

读法：`get` 传入 ID，返回一个 Effect——成功产出 `Info`，可能失败 `NotFoundError`，无额外依赖（`R` 省略默认 `never`）。

**关键心智**：`Effect` 只是描述，未执行。执行入口在 runtime 层——opencode 实测三种入口（core/src 计数）：`runFork`（23 处，后台任务主力）、`runPromise`（11 处，与 Promise 世界交接）、`runSync`（8 处，同步解码等）。

## 2. 串联计算：`Effect.gen` + `yield*`

仓内最主流写法（core/src 实测：`yield*` 4,119 处、`Effect.gen` 539 处、`Effect.fn` 745 处）。

不用 `gen` 的替代品是 `.pipe(Effect.flatMap(...))` 层层嵌套（callback hell 的 FP 版）；`gen` + `yield*` 让代码看起来像 Go 的顺序执行：

```ts
// packages/core/src/session/session.ts:52-56
const get = Effect.fn("Session.get")(function* (sessionID: SessionSchema.ID) {
  const session = yield* store.get(sessionID)
  if (!session) return yield* new NotFoundError({ sessionID })
  return session
})
```

| 片段 | 作用 | Go 对照 |
|---|---|---|
| `Effect.fn("名字")(fn)` | 给函数命名（日志/追踪可见） | 函数名 |
| `function*` | generator 函数（JS 语法） | 普通函数 |
| `yield* effect` | 取成功值；**失败自动中断向上传播** | `v, err := f(); if err != nil { return err }` 的合体 |
| `return yield* new NotFoundError(...)` | 以类型化错误失败 | `return nil, &NotFoundError{...}` |

**一个常见误解的澄清**：`yield*` 一个会失败的 Effect，**不会**因"未处理错误"报编译错——错误隐式累积进外层 `gen` 的 `E`（取并集）。真正报错的是**签名不诚实**：

```ts
const process = (id: string): Effect.Effect<void, never> =>  // 声明"绝不失败"
  Effect.gen(function* () {
    const user = yield* getUser(id)  // 实际可能 NotFoundError
    // ❌ 编译错：声明的 never 与实际的 NotFoundError 不匹配
  })
```

Effect 不逼你在 `yield*` 处显式 catch，而是逼你在**类型签名上诚实**——要么 `E` 带上错误，要么 `catchTag` 显式消掉。

## 3. 类型化错误：`TaggedError` + `catchTag`

### 定义：`Schema.TaggedError`

```ts
// packages/core/src/session/error.ts:10-88（13 个 Session 错误类）
export class NotFoundError extends Schema.TaggedError<NotFoundError>()("Session.NotFoundError", {
  sessionID: SessionSchema.ID,
}) {}
```

- 带全局唯一标签（`_tag = "Session.NotFoundError"`）+ 结构化字段（`sessionID`）
- core/src 实测 **108 处**、17 个文件；注意 API 是 `Schema.TaggedError`（4.0.1 惯用形）

### 捕获：按标签精确处理

```ts
// packages/core/src/file-mutation.ts:92
Effect.catchTag("Environment.NotFound", () => Effect.succeed(false))
// packages/core/src/permission.ts:253 —— 拒绝权限升格为致命缺陷
Effect.catchTag("Permission.DeclinedError", (error) => Effect.die(error))
```

- `catchTag("标签", handler)`：命中该标签才处理，其余错误**原样继续传播**（core/src 45 处）
- 多标签批量处理用 `catchTags`（3 处：plugin/host.ts、persistent-pty、tool/mcp.ts）
- `orDie`：把可恢复错误变致命缺陷（≈ panic，50+ 处，通常用于"这里不该错"的防御性收尾）

> **Go 对照**：`catchTag` ≈ `errors.As(err, &TargetError{})` + 类型安全的 handler 入参。区别是 Effect 的错误类型在签名里，漏处理能在类型上看出。

## 4. 依赖注入：`Context.Service` + `Layer`

### 三者本质（初学者最易混淆）

| 概念 | 是什么 | 是"蓝图"吗 | Go 类比 |
|---|---|---|---|
| `Effect<A,E,R>` | 描述**一段计算** | ✅ 计算蓝图 | 惰性闭包 `func() (A, error)` |
| `Layer<A,E,R>` | 描述**如何构建服务** | ✅ 构建蓝图 | 构造函数 `func(deps) (A, error)` |
| `Service` | 服务的**名字/标识** | ❌ 是标签 | 接口类型名 + 注册 key |

### 标准三段式（全仓 151 个 Service 定义）

**第一步：定义服务标识**

```ts
// packages/core/src/bus.ts:172
export class Service extends Context.Service<Service, Interface>()("@opencode/Bus") {}
```

**第二步：构建服务（Layer + 依赖声明）**

```ts
// packages/core/src/config.ts:79 —— 10+ 个依赖全部具名绑定
Layer.effectContext(
  Service,
  Effect.gen(function* () {
    const initial = yield* Ref.make(initialConfig)
    const updates = yield* PubSub.unbounded<Watcher.Update>()
    const fs = yield* FSUtil.Service        // 每个 yield* 都是依赖声明
    const location = yield* Location.Service
    const watcher = yield* Watcher.Service
    const bus = yield* Bus.Service
    // ...
  }),
)
```

**第三步：组合与增强**

```ts
// packages/core/src/instance.ts:172-179
Layer.tap((context) => Effect.addFinalizer(() => /* 生命周期收尾 */)),
Layer.tap(() => Effect.logInfo("location services booted", { directory: ref.directory, /* ... */ })),
```

- `Layer.provide(dep)`：注入依赖（≈ 构造函数传参）
- `Layer.tap(fn)`：构建后副作用（打日志/注册清理）
- `Layer.unwrap`：从 Effect 中取出 Layer 动态提供（5 处）
- 注意：**仓内不用 `Layer.fresh`**（0 处）——缓存控制走自建的 LayerNode 体系

### 进阶：opencode 自建的 LayerNode / LayerMap（非 Effect 标准库）

读 opencode 源码的"抽象感"很大部分来自这层自建抽象：

- **LayerNode**（`packages/util/src/effect/layer-node.ts`，330 行）：类型化依赖图——`makeGlobalNode`（进程级单例，如 Worktree/Job）vs `makeLocationNode`（每 Location 一份，如 Config/Tool/Skill，core 里 16+ 处）；`LayerNode.compile(root, { replacements, shared })` 把图编译成 Layer，`Node.replace` 支持测试替换
- **LayerMap**（`location-services.ts:56`）：按 `Location.Ref`（目录引用）缓存整套 Location 服务；**TTL 是 `Duration.infinity`**（不自动过期，与"闲置 60 分钟释放"的早期版本不同）

> 这层只在读 opencode 源码时需要；用 Effect 写自己的项目可以跳过。

## 5. 并发：`forkScoped` + `Effect.all` + `forkIn`

| API | core/src 计数 | Go 对照 |
|---|---|---|
| `Effect.forkScoped` | **75**（唯一主流 fork） | `go func()` 但自动绑定作用域、可取消、不泄漏 |
| `Effect.all` | 23 | `goroutine + WaitGroup + 收集结果` |
| `Effect.forkIn(scope)` | 20 | 指定生命周期归属的 `go`（配合显式 Scope） |
| `Effect.forkDaemon` | **0**（不用） | —— |

```ts
// packages/core/src/session.ts:343 —— 并发取多个结果
const result = yield* Effect.all({ /* 多个 Effect 并发 */ })

// packages/core/src/session/runner/step.ts:133 —— 工具调用 fork 到作用域
).pipe(Effect.forkScoped),
```

关键优势：Fiber 挂在 Scope 上，作用域结束**强制取消**——从机制上杜绝 goroutine 泄漏。`forkDaemon`（不受作用域管）全仓零使用，反映"一切并发必须可清理"的纪律。

## 6. 流式：`Stream`（LLM 输出的载体）

`Stream` 是 `Effect` 的流式版——同样惰性/可组合/类型安全，元素是多个。core/src 196 处 `Stream.*`。

核心场景就是 LLM 流式输出（`session/runner/step.ts:107-137`）：

```ts
const providerStream = llm.stream(input.prepared.request, input.prepared.options).pipe(
  Stream.runForEach((event) =>
    Effect.gen(function* () {
      // 逐事件处理：文本 delta / 工具调用……
      toolRuns.push({
        call: event,
        fiber: yield* Effect.uninterruptibleMask((restore) =>
          restore(executeTool(event)).pipe(
            Effect.catchTag("Tool.Error", /* ... */),
          ),
        ).pipe(Effect.forkScoped),      // 工具并发执行、挂作用域
      })
    }),
  ),
  Effect.ensuring(publisher.flush()),    // 无论成败最终冲刷事件
)
```

> **Go 对照**：`Stream` ≈ `chan`，但自带背压、可安全关闭、可组合（`Stream.map/filter/merge`）；`runForEach` ≈ `for x := range ch { f(x) }`。

## 7. 资源安全：`addFinalizer` + `acquireRelease`

跨作用域/跨并发的资源清理不靠自觉，靠 Scope 机制：

```ts
// packages/core/src/pty.ts:128 —— 会话结束清理 PTY
yield* Effect.addFinalizer(() => cleanup)

// packages/core/src/git.ts:609 —— 获取/释放配对
yield* Effect.acquireUseRelease(acquire, use, release)
```

| API | core/src 计数 | Go 对照 |
|---|---|---|
| `Effect.addFinalizer` | 43（36 个文件） | `defer`，但可挂任意 Scope、出错/取消也执行 |
| `acquireRelease`/`acquireUseRelease` | ~14 | `defer release()` 的配对强化版 |

## 8. 学习路径 + 频率实测

### 学习路径（别跳级）

```
第 1 步：Effect<A, E, R> 三泛型          ← 一切的基础
第 2 步：Effect.gen + yield* + Effect.fn ← 立刻能读懂 80% 的代码
第 3 步：TaggedError / catchTag / orDie  ← 错误类型化
第 4 步：Context.Service + Layer         ← 最抽象但最核心
第 5 步：forkScoped / Effect.all         ← 需要并发时
第 6 步：Stream / addFinalizer           ← 按需
第 7 步：LayerNode / LayerMap            ← 只为读 opencode 源码
```
