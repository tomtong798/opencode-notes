# SolidJS 响应式机制（Reactivity in Practice）

> 一句话：**Solid 的响应式不靠组件重渲染，而靠信号图上精确到属性的依赖追踪——opencode 的 TUI 和桌面端把这套机制用作从 SSE 事件流到终端像素的完整数据管道。**
> 基线：v2.0.30，dev 分支；行号实测（2026-10-20）。
> 前置 [2.0_reactivity.md](2.0_reactivity.md)（概念）| 主篇 [2_solidjs.md](2_solidjs.md）（概览）

## 0. opencode 里的响应式地图（哪些层在用）

```
opencode 仓库中 Solid 响应式的分层
├── packages/client/src/solid/          ← 数据层（无 UI）
│   ├── connection.ts   SSE 事件 → publish() 10ms 缓冲 → batch 分发
│   └── data.ts         createStore 投影：事件 → store（produce/reconcile）
├── packages/tui/                       ← 终端 UI（@opentui/solid 渲染）
│   ├── src/context/    createSimpleContext 包装的 Provider 群
│   ├── src/routes/     session/index.tsx（2000+ 行的信号密集区）
│   └── src/ui/         toast.tsx / animation.ts / pane-resize.ts
├── packages/app/                       ← 桌面 UI（新会话向导等）
│   └── src/new-session/ controller.ts 里 createMemo 级联链
└── packages/session-ui/                ← 复用组件（<For> 渲染列表）
```

要点：**响应式不是"UI 框架特性"，而是贯穿 client → app/tui 的数据流骨架**。事件在 connection 层被批量、在 data 层被投影进 store、在组件层被 memo/effect 消费——每一层都只是信号图上的节点。

## 1. 核心 API：signal/memo/effect（真实用例逐个）

### 1.1 createSignal

最朴素的原子状态。`packages/tui/src/ui/toast.tsx:29`：

```ts
const [hovered, setHovered] = createSignal(false)
```

同文件 `:188` 用 getter 暴露给 context 消费者（注意是 `get` 访问器，不是一次性取值——见 §5）。

带选项的用例，`packages/tui/src/ui/animation.ts:63`：

```ts
const [value, setValue] = createSignal(clone(initial), { equals: false })
```

`equals: false` 让"值相等也通知"——动画每帧写入同值对象也要触发渲染，绕过默认的相等性短路。

信号密集区见 `packages/tui/src/routes/session/index.tsx:280-295`：`rowsSynced` / `navigationSlack` / `synced` / `awayFromBottom` / `latestHovered` 五个布尔/数值信号各自独立追踪滚动状态，互不牵连。

### 1.2 createMemo

`packages/app/src/new-session/workspace/controller.ts:71-184` 是教科书级的 memo 级联：

```ts
const currentProject = createMemo(() => { ... })        // L71
const worktreeItems = createMemo(() => { ... })         // L106
const worktreeDirectories = createMemo(() => { ... })   // L117
const managedWorktrees = createMemo(() => { ... })      // L133
const visible = createMemo(() => ...)                   // L143
const selected = createMemo(() => { ... })              // L150
const value = createMemo(() => ...)                     // L176
```

七层 memo 链：上游信号（选中项目）变 → 只重算受影响的下游 memo，且 memo 值本身有缓存——依赖不变就零计算。React 的 `useMemo` 每次渲染都可能重算，Solid 的 memo 只在依赖变更时算一次。

`packages/client/src/solid/data.ts:281`：

```ts
const sessions = createMemo(() =>
  Object.values(store.session.info).toSorted((a, b) => b.time.updated - a.time.updated),
)
```

store 的 `session.info` 字典 → 排序后的会话列表，一个 memo 完成投影。任何 `session.info` 子键变更都会触发它，但只有真正读取该子键的组件才会更新。

### 1.3 createComputed + on(..., { defer: true })

`createComputed` 是"立即、同步"的 effect（在下一个 effect 之前运行），适合"信号 → 命令式 API"的桥接。两个实测用例：

**用例 A：瞬态重置**，`packages/app/src/session/timeline/cache.ts:68`：

```ts
createComputed(on(session.identity.workspaceKey, syncWorkspace, { defer: true }))
```

身份（workspace）切换时清空 timeline 缓存。`{ defer: true }` 表示初次执行跳过——只在 key **变化**时清缓存，初始加载不算切换。（5_timeline 笔记提过的正是这一处。）

**用例 B：模式同步**，`packages/tui/src/context/keymap.tsx:425-426`：

```ts
const current = createMemo(() => stack().findLast((item) => item.enabled())?.mode ?? MODE.base)
// Publish mode changes before another command can be dispatched in the same callback.
createComputed(() => keymap.setData(MODE.key, current()))
```

信号栈 → keymap 的命令式 `setData`。注释点明选 `createComputed` 而非 `createEffect` 的原因：**必须在同一回调里后续命令派发之前完成发布**——effect 是异步调度的，computed 是同步的。

### 1.4 createEffect + onCleanup

`packages/app/src/new-session/screen.tsx:81-86` 两个 effect，第一个还配了显式 `on`：

```ts
createEffect(
  on(composer.ready, (ready) => {
    if (ready) model.restoreFocus()
  }),
)
createEffect(() => {
  if (!composer.ready()) return
  untrack(() => { /* 把 URL 里的 prompt 注入 composer，一次性 */ })
})
```

`onCleanup` 的真实用例，`packages/tui/src/config/index.tsx:371`：

```ts
onCleanup(() => watcher?.close())
```

文件 watcher 随配置 Provider 的 owner 销毁而关闭——Solid 的所有权树（owner tree）让资源清理不需要 React 的 useEffect-return-cleanup 心智：任何计算上下文里都能挂 `onCleanup`。

## 2. Store 三件套：createStore/produce/reconcile（以 data.ts 投影为例）

`packages/client/src/solid/data.ts` 是全仓库最重的 store 使用现场（2000+ 行）。

### 2.1 createStore

`data.ts:259-275`：

```ts
const [store, setStore] = createStore<Store>({
  session: { info: {}, family: {}, active: {}, message: {}, messageCursor: {},
             messageLoading: {}, pending: {}, permission: {}, form: {} },
  project: { info: {}, permission: {} },
  location: {},
})
```

Store 是**按路径代理**的：`store.session.info` 的每个 key 都是独立信号。读 `store.session.info[某id].title` 只订阅这一条路径——其他会话更新不惊动你。

### 2.2 produce：细粒度就地变更

`data.ts:484` 定义了 editText 投影，`:952-955` 是事件消费侧：

```ts
// data.ts:484
editText(sessionID: string, messageID: string, fn: (text: SessionMessageAssistantText) => void) {
  message.editAssistant(sessionID, messageID, (assistant) => {
    const text = assistant.content.findLast((item): item is SessionMessageAssistantText => item.type === "text")
    if (text) fn(text)
  })
},
// data.ts:952-955（事件 switch 里）
case "session.text.delta":
  message.editText(event.data.sessionID, event.data.assistantMessageID, (text) => {
    text.text += event.data.delta
  })
  return
```

等等——`text.text += event.data.delta` 看起来就是"直接改"。**这里能工作的前提是它跑在 produce 里**（`message.editAssistant` 内部经 `message.update` → `setStore(..., produce(...))`）。区别在于：

```
直接赋值（错误）                produce 包裹（正确）
────────────────────────      ────────────────────────────
text.text += delta            produce((draft) => {
代理被脱钩：mutation             draft.text.text += delta
发生在原始对象上，              })  → Solid 的代理拦截写入，
Solid 感知不到 →                精确通知 text.text 的订阅者
订阅组件不更新
```

在 produce 的 draft 里，你写的是看似普通的 mutable 代码，但每一步属性写入都被代理记账，转成对应路径的细粒度信号更新。**规则：store 的深层对象要么用 setter 路径写（`setStore("a","b",v)`），要么整体 produce，绝不裸改。**

### 2.3 reconcile：结构共享的列表同步

全量数据（fetch 回来的消息列表）不能用 produce 逐条改——用 `reconcile` 做 diff 换入。`data.ts:1712`（消息分页拉取完成时）：

```ts
batch(() => {
  messageIndex.set(sessionID, new Map(messages.map((message, index) => [message.id, index])))
  setStore("session", "message", sessionID, reconcile(messages))
  setStore("session", "messageCursor", sessionID, response.cursor.next ?? undefined)
})
```

`reconcile(messages)` 把新数组与旧状态**逐节点 diff**：引用相等的子树原样保留（结构共享），只有真正变化的节点被替换。效果：拉取 100 条消息回来，其中 3 条变了 → 只有那 3 条的订阅组件更新，其余组件连比较都不需要。其他实测点：`:650`（active 会话快照）、`:669`（project info）、`:1393`/`:1776`（消息列表）、`:1878`（全项目表）。

选择口诀：**流式增量（delta 事件）→ produce；快照全量（fetch 结果）→ reconcile**。

## 3. batch：事件批量与一次渲染

`packages/client/src/solid/connection.ts:65-74`：

```ts
function publish(event: OpenCodeEvent) {
  pending.push(event)
  if (flushTimer) return
  flushTimer = setTimeout(() => {
    flushTimer = undefined
    const events = pending
    pending = []
    batch(() => events.forEach(options.onEvent))
  }, options.flushInterval ?? 10)
}
```

机制（SSE 连接本身见 [../../5_timeline/4_renderer-boot.md](../../5_timeline/4_renderer-boot.md)，此处只讲响应式侧）：

```
SSE burst（一帧内 N 个事件）
│
├─ publish(e1) ── 入 pending，设 10ms 定时器
├─ publish(e2..eN) ── 只入队（flushTimer 已存在，直接 return）
│
└─ 10ms 后定时器触发
   └─ batch(() => events.forEach(onEvent))     ← connection.ts:72
      │
      ├─ 事件逐个走 data.ts 的 switch → produce/reconcile 写 store
      └─ batch 结束：只做一次依赖通知传播
         → 每个受影响的组件只重求值一次，渲染一帧
```

没有 batch 会怎样：每个 `onEvent` 里的 store 写入各自触发一轮通知传播，N 个事件 = N 轮、N 次渲染。batch 把"写"和"通知"解耦——批内所有写入先落盘，通知在批尾统一合并去重。TUI 层同样自觉使用：`packages/tui/src/app.tsx:633`、`ui/dialog.tsx:312/327`、`routes/session/index.tsx:840-855` 都是"一个用户动作改多个状态"时包 batch。

## 4. 控制流组件与 keyed 语义

Solid 的 `<For>`/`<Index>`/`<Show>` 是**编译期展开的响应式原语**，不是运行时组件（没有组件实例重渲染这回事）。

**`<For each={list()}>` 按 item 引用 keyed**：列表变化时，Solid 用 `===` 追踪每个 item，存活 item 的渲染函数连同其内部信号**原样保留**，只增删移动。`packages/app/src/servers/registry/row-items.tsx:10`：

```tsx
<For each={items()}>
```

`packages/app/src/new-session/project/selector.tsx:419-440` 三层嵌套 `<For>` 渲染项目/服务器树，靠的就是 keyed：列表刷新时未变项的展开状态、局部信号全部保住。**key 的意义就是细粒度更新：引用没变的项零开销**——这也是为什么 `For` 的 each 里放"每次 map 新建对象"的列表会退化成全量重建。

**`<Index each={calls()}>` 按下标 keyed**：适合"项本身无稳定身份、或项是原始值"的列表。`packages/tui/src/routes/session/index.tsx:3259`：

```tsx
<Index each={calls()}>{(call) => <ExecuteCallView call={call} />}</Index>
```

tool call 流式追加场景：新 call 追加到尾部只影响新下标；但若中间插入，下标后的项会"错位"复用——项有稳定 id 时永远选 `<For>`。

**`<Show when={cond}>`**：条件成立才创建子树（lazy），切换即销毁/重建子 owner 树（连带 onCleanup）。

## 5. 组件只跑一次的推论（props 规则）

Solid 组件函数**只执行一次**——没有 re-render。推论：**解构 props 会把 getter 冻结成当时的值，响应性当场死亡**。

仓库里的合规示范：

- **getter 传递**，`packages/app/src/new-session/screen.tsx:36-37`：

  ```ts
  const workspace = createNewSessionWorkspaceController({
    selectedWorktree: () => draftTab()?.worktree,   // ← 传函数，不传值
    selectedBranch: () => draftTab()?.branch,
  })
  ```

- **mergeProps**，`packages/tui/src/context/args.tsx:20`：

  ```ts
  return mergeProps(props, { /* 默认值 */ })
  ```

  合并后仍是懒求值的代理对象，读取时才解引用，默认值与传入 props 都保持响应。

- **splitProps**，`packages/tui/src/component/patch-diff.tsx:39`：

  ```ts
  const [local, diffProps] = splitProps(props, ["diff", "hunkFg", "lineNumberBg", "ref", "scroll", "gutterPadding"])
  ```

  拆分而非解构——两边都是保持响应的 props 子集，适合"本地消费一部分、透传其余"。

- **对象暴露用 getter**，`packages/tui/src/ui/toast.tsx:186-192`：

  ```ts
  return {
    get currentToast() { return store.currentToast },
    get pending() { return store.queue.length },
  }
  ```

  消费方每次访问 `toast.currentToast` 都在访问活信号。

另外 `packages/app/src/new-session/screen.tsx:86-93` 演示了 `untrack` 的规范用法：effect 里读 `composer.ready()` 做守卫后，把不该建立依赖的写入包进 `untrack(() => {...})`——防止 effect 意外订阅 composer 内部状态导致重复触发。

## 6. Context 与 createSimpleContext

`packages/tui/src/context/helper.tsx:3-27` 的完整实现：

```tsx
export function createSimpleContext<T, Props extends Record<string, any>>(input: {
  name: string
  init: ((input: Props) => T) | (() => T)
}) {
  const ctx = createContext<T>()
  return {
    context: ctx,
    provider: (props: ParentProps<Props>) => {
      const init = input.init(props)
      return (
        // @ts-expect-error
        <Show when={init.ready === undefined || init.ready === true}>
          <ctx.Provider value={init}>{props.children}</ctx.Provider>
        </Show>
      )
    },
    use() {
      const value = useContext(ctx)
      if (!value) throw new Error(`${input.name} context must be used within a context provider`)
      return value
    },
  }
}
```

三个设计点：**① init 在 Provider 组件体里跑一次**（组件只跑一次 → 初始化逻辑天然只执行一次，相当于 React 的 useMemo+useRef 合体，且挂在 owner 树上可被 onCleanup 回收）；**② `<Show when={init.ready}>` 门控**：初始化未就绪（如异步数据未达）时干脆不渲染子树，子组件拿到的 context 永远是就绪态；**③ use() 强校验**：缺 Provider 直接抛带名字的错误。

全 TUI 统一走这个模式（`grep createSimpleContext packages/tui/src/context/` 实测十余处）：`route.tsx:29` 的 `useRoute`、`prompt.tsx:4` 的 `usePromptRef`、`data.tsx:11` 的 `useData`、`session-tabs.tsx:56`、`update-notification.tsx:28` 等。这是"context 即服务"的惯用法——每个 context 文件导出 `{ use, provider }` 对，Provider 隐藏 `<Show>` 细节。

## 7. React → Solid 心智迁移表

| React 心智 | Solid 对应 | opencode 实证 | 关键差异 |
|---|---|---|---|
| setState 触发组件重渲染 | setSignal/setStore 只触发依赖重求值 | toast.tsx:29 | 没有 render 函数重跑这回事 |
| setState(p => ...) 不可变更新 | setStore 路径写 或 produce 就地改 | data.ts:953 | produce 里可变写法更自然 |
| 全量快照 setState | reconcile(新快照) 结构共享 diff | data.ts:1712 | 只替换变化子树 |
| useMemo（每次渲染可能重算） | createMemo（依赖变更才算） | controller.ts:71-184 | memo 是真缓存不是提示 |
| useEffect（提交后异步） | createEffect（异步）/ createComputed（同步） | keymap.tsx:426 | 需要同步发布时选 computed |
| useEffect 依赖数组手写 | 自动依赖追踪，无需声明 | cache.ts:68（配 on 显式化） | on() 是收紧不是必需 |
| useEffect return 清理 | onCleanup（任何计算上下文可挂） | config/index.tsx:371 | 挂在 owner 树上 |
| key={id} + 列表 diff（VDOM） | `<For>` 按 item 引用追踪 | row-items.tsx:10 | key 是机制本身不是 prop |
| 数组下标渲染也用 map | `<Index>` 显式声明按下标 | session/index.tsx:3259 | 语义分裂，选错有性能/状态坑 |
| useState 初值只算一次（惰性 init） | createSignal(exp) 的 exp 只算一次 | pane-resize.ts:12 | 一致，但注意组件体也只跑一次 |
| 解构 props 再用 | 必须保留 props 对象/getter | args.tsx:20 mergeProps | 解构 = 响应性死亡 |
| 状态提升 + props 层层传 | context/信号直接传 accessor | helper.tsx createSimpleContext | 传函数引用零成本 |
| React 18 automatic batching | 显式 batch(() => ...) | connection.ts:72 | Solid 需要手动包，但覆盖异步批 |
| shouldComponentUpdate 性能优化 | 不需要——没有组件级渲染 | data.ts:281 memo 投影 | 细粒度订阅天然跳过无关更新 |
