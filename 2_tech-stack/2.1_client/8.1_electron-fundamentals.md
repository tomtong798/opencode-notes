## 1. Electron 是什么

用 **Web 技术（TS/HTML/CSS）构建跨平台桌面应用**的开源框架：把 **Chromium（渲染）+ Node.js（系统能力）** 打进同一个可分发程序。代表产品：VS Code、Slack、Discord、Figma 桌面端。

> **底层三件与 V8 共享**：Chromium 和 Node.js 各自内嵌一份 V8 引擎——Electron 构建让二者**共享同一个 V8 实例**，避免重复加载内存。分工：Chromium 画界面（DOM/布局/GPU），Node 给系统能力（fs/进程/网络），V8 是两者共同的 JS 执行心脏。

| 特性 | 说明 |
|---|---|
| 跨平台 | 一套代码跑 Windows/macOS/Linux |
| Web 栈复用 | 前端代码近乎零成本上桌面 |
| 系统能力 | 经主进程访问文件/托盘/通知/原生菜单 |
| 代价 | 包体大（带着 Chromium）、内存占用高、需自管安全 |

vs 竞品：**Tauri**（Rust 后端 + 系统 WebView，包小但 WebView 一致性差）、**PWA**（零分发成本但系统能力受限）。Electron 的胜负手是**一致性**（自带浏览器）与**生态成熟度**。

## 2. 多进程模型：为什么不是一个进程

历史包袱决定架构：Chromium 的渲染引擎设计为**不可信任页面跑在沙箱进程**，Node 又需要完整系统能力——二者不能同进程（安全模型冲突）。Electron 的解法：

```
┌─ 主进程（Main，Node.js 环境，唯一）────────────────┐
│ 窗口生命周期、原生菜单、托盘、IPC 服务端、系统 API    │
│ opencode 对应：src/main/*（Effect Layer 在这里跑）    │
└──────────┬──────────────────────────────────────┘
           │ 每个 BrowserWindow 一个
┌──────────▼──────────────────────────────────────┐
│ 渲染进程（Renderer，Chromium 沙箱，×N）             │
│ 跑你的 Web 应用；默认无 Node、无页面外访问          │
│ opencode 对应：加载 @opencode/app（与 Web 端同代码）│
└──────────┬──────────────────────────────────────┘
           │ 加载页面前注入
┌──────────▼──────────────────────────────────────┐
│ preload 脚本（跑在 renderer 进程内的隔离世界）       │
│ contextBridge 暴露受控 API；不是独立进程            │
│ opencode 对应：src/preload/index.ts（仅 32 行）     │
└─────────────────────────────────────────────────┘
另：Chromium 自动拉起 GPU/Utility 辅助进程（应用不管理）
```

**关键认知**：

- **preload 不是进程**——是 renderer 进程里 `contextIsolation` 开启后的隔离世界，页面 JS 碰不到它内部的东西，只能用它显式暴露的接口
- **渲染进程默认零 Node 能力**（`contextIsolation: true` 下）——它只有 preload 经 `contextBridge` 暴露的自定义 API；preload 本身也只能用 `ipcRenderer` 等受限模块（能转发请求，不能 `require('fs')` 执行操作），真正的 Node 执行全部发生在主进程
- 渲染进程崩溃只死一个窗口，主进程不死——故障隔离是多进程的直接收益
- 主进程是"单点政府"：所有系统能力经它中转，这也是它常成性能瓶颈的原因（opencode 用"业务数据不过 Main"规避，见架构篇）

> **一句话心智模型**：Electron ≈ 拿 Chromium 的多进程架构，把"浏览器进程"替换成 Node.js 运行时，"标签页"保留为渲染进程——所以每个窗口是一个独立 Chromium 渲染进程，而"管理标签页的那个进程"手里握着 Node。

## 3. 进程间通信（IPC）的演进

| 世代 | 机制 | 特点 |
|---|---|---|
| 早期 | `ipcRenderer.send/invoke` 直连 | 需在 preload 逐个转发，接口发散 |
| 近代 | `contextBridge + ipcRenderer.invoke` | 白名单化，但 JSON 序列化开销 |
| 现代（opencode 现状） | **MessageChannelMain/MessagePort + RPC 协议** | structured clone（无 JSON 开销）；端口转交后 Main↔Renderer 直通，契约集中在一份 RPC 定义（opencode：Effect RPC 线协议，7 组 50+ RPC） |

opencode 的选择可作参考：**IPC 通道只有一条（MessagePort RPC），业务数据不进 Main**——renderer 与后端服务直接 HTTP 通信，Main 只管系统能力与鉴权注入。

## 4. 安全基线（Electron 官方清单的实践版）

所有窗口必须：

```ts
webPreferences: {
  contextIsolation: true,   // ① 页面与 preload 隔离（contextBridge 可用的前提）
  nodeIntegration: false,   // ② 渲染进程禁 Node
  sandbox: true,            // ③ Chromium 沙箱
}
```

加码项（opencode 均有落地）：

- **导航策略**：拦截非自有协议跳转（`will-navigate`/`setWindowOpenHandler`）
- **凭据隔离**：敏感凭据只存主进程，renderer 请求经 `webRequest.onBeforeSendHeaders` 注入鉴权头——密码不跨进程边界
- **CSP**：渲染页面内容安全策略
- 常见错误清单：关 contextIsolation"图省事"、`nodeIntegration: true` 调试上线忘关、webview 标签未限权、`disablewebsecurity`——每一个都是真实漏洞来源

## 5. 打包与分发

| 工具 | 定位 | opencode 选择 |
|---|---|---|
| **electron-builder** | 配置驱动的打包器：出 dmg/nsis/AppImage/deb/rpm，含签名/公证/自动更新清单 | ✅（`electron-builder.config.ts`） |
| Electron Forge | 官方全家桶（脚手架+打包） | — |

打包关注点：

- **目标产物**：macOS `dmg`+`zip`（hardened runtime + 公证）、Windows `nsis`（代码签名）、Linux `AppImage`+`deb`+`rpm`
- **原生模块**：node-pty 等 .node 模块需按目标平台/electron ABI 重编（electron-rebuild；opencode 用 `@lydell/node-pty` 分发预编译绑定规避）
- **资源内嵌**：`extraResources` 携带 CLI 二进制等大件（opencode：`opencode-cli` 随包分发，运行时 staging 到 userData）
- **协议注册**：`protocols: { schemes: ["opencode"] }` 注册深链

## 6. 自动更新

`electron-updater`（electron-builder 配套）：读更新源上的 `latest*.yml` 清单比对版本 → 下载差分/全量 → 重启安装。更新源自托管（generic provider）。opencode：更新元数据由 `services/update`（Cloudflare Worker + D1）提供，按通道（dev/beta/stable）分流。

## 7. 性能要点（桌面端常见问题）

- **启动**：主进程入口保持极小、重模块懒加载、**窗口先行**（先上屏再初始化——opencode `index.ts` 35 行就是为此）
- **IPC**：避免高频大数据过 Main（JSON 序列化是热点；MessagePort structured clone 更快；业务数据直连后端最优）
- **内存**：多窗口=多 Chromium 实例；及时销毁窗口、复用 render process
- **磁盘**：SQLite 用 WAL；写盘走 write-behind 去抖（opencode storage 层范式）

## 8. 常见误区与排障速查

### 误区 → 纠正

| 误区 | 纠正 |
|---|---|
| 渲染进程有"受限 Node 接口" | 渲染进程**默认零 Node 能力**；只有 preload 暴露的自定义 API，Node 执行全在主进程 |
| preload 运行在主进程 | 它跑在 renderer 进程内的隔离世界，只有 `ipcRenderer` 等受限模块 |
| 主进程在 Chrome 里"开标签页" | 主进程经 Chromium 多进程机制 **fork 出渲染进程**，不是开标签页 |
| 一个窗口一个主进程 | 全应用只有一个主进程 |
| 主进程能做所有事 | 主进程不做界面渲染；且业务数据走它反而成瓶颈 |

### 排障（症状 → 方向）

| 症状 | 方向 |
|---|---|
| 白屏 | 开发者工具看 renderer console；确认协议/资源路径 |
| preload 未生效 | `contextIsolation` 是否开启；preload 路径是否绝对 |
| IPC 不通 | MessagePort 是否在 `did-finish-load` 后转交；契约版本是否一致 |
| 原生模块报错 | ABI 不匹配（用 electron 版本的 headers 重编） |
| 更新失败 | `latest*.yml` 是否可达；签名/公证是否通过 |
