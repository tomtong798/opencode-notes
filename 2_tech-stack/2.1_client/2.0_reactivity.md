# 响应式编程（Reactivity）

> 一句话：**状态变了，UI 自动跟着变——你只描述"UI 是状态的函数"，框架负责"谁订阅了什么、变了通知谁"。**
>
> 定位：概念前置篇——先懂"状态如何自动传播"，再看 [2_solidjs.md](2_solidjs.md)（实现）与 [2.1_solidjs-reactivity.md](2.1_solidjs-reactivity.md)（SolidJS 机制实战）。

---

## 1. 命令式 vs 声明式：响应式要解决什么

同一个需求：**点击按钮，计数显示 +1**。

### 命令式：你亲自操刀每一步

```typescript
let count = 0;
const label = document.getElementById("count-label")!;
const btn = document.getElementById("inc-btn")!;

btn.addEventListener("click", () => {
  count += 1;                                   // 1. 改状态
  label.textContent = `Count: ${count}`;        // 2. 亲手找到节点、亲手改 DOM
});
```

问题不在代码量，而在**规模化之后**：

- `count` 被页面 5 处引用？你得记住 5 个节点、写 5 行更新代码，漏一处就是 bug
- 状态之间有派生关系（`double = count * 2`）？每次变更都要手动维护所有派生值
- **状态与视图的同步责任全在人脑**——这正是响应式要消灭的错误来源

### 声明式：只描述 UI = f(state)

```tsx
// React / Solid 语法几乎一样
const [count, setCount] = useState(0);

<button onClick={() => setCount(count + 1)}>+</button>
<div>Count: {count}</div>   // 只是"声明"：这个位置显示 count
```

没有任何一行"去改 DOM"的代码。你只声明**映射关系**，剩下的交给框架。

于是核心问题浮出水面——**状态变了，谁负责更新 UI？怎么知道该更新哪里？**

这就是所有响应式框架回答的同一道题，答案的不同造就了下面的流派分歧。

## 2. 拉 vs 推：两个基本模型

### Pull（拉）：React 模型——"别急，我下次渲染时自己来读"

状态变更不直接通知 UI，只是标记"脏了"（schedule render）；等调度时机到了，框架**重新执行组件函数**，拿新状态返回的新 vdom，与旧 vdom **diff** 出要改的地方。

```
 Pull（拉）—— React                          Push（推）—— Signals/Vue
 ┌────────┐   setCount()   ┌────────┐        ┌────────┐  setCount(2)  ┌─────────┐
 │ setState├────标记脏──────▶ 调度批处理        │ signal ├─────立即──────▶ 订阅者A  │
 └────────┘                └────┬───┘        │ count=2│   精确通知     │ <div>  │
                                │            └───┬────┘               │ 递增执行 │
                           重跑整个组件函数         │ 未订阅者B ◀── 不通知 ─┘ └─────────┘
                                │
                           新旧 vdom diff
                                │
                           最小 DOM 操作
```

### Push（推）：状态变更立即、精确地通知订阅者

谁读了 `count`，谁就登记为订阅者；`count` 变了，只通知这些订阅者，且附上新值。

| 维度 | Pull（React） | Push（Signals/Vue） |
|---|---|---|
| 通知时机 | 调度批处理后统一处理 | 赋值瞬间（可再批处理） |
| 更新单位 | 组件（重跑函数） | 订阅了该值的表达式/DOM 绑定 |
| 计算浪费 | 组件内没变的分支也被重算 | 只执行真正依赖的表达式 |
| 好处 | 不可变快照、时间旅行、心智简单 | 跳过无关计算、无需 diff |

两个常见误解先澄清：

- **拉模型 ≠ 没有响应式**。React 当然是响应式的——`setState` 触发 UI 自动更新，完全符合"状态变了 UI 跟着变"。区别只在粒度：它的更新单位是**组件**，靠 diff 找出精确落点。
- **推模型 ≠ 每次赋值同步刷 DOM**。Solid/Vue 都会在微任务里做批处理：同一个 tick 内多次赋值合并成一次传播（glitch-free：订阅者不会看到中间态）。推的是"标记脏 + 精确调度"，不是"赋值一行就同步跑十行"。

注意：拉模型不是"没有响应式"——React 当然是响应式的，只是粒度**粗到组件级**，靠 diff 找出精确更新点。推模型把粒度**做细到值级**，diff 就可以省掉。

## 3. 依赖收集通论：读时追踪、写时通知

推模型的引擎只有一个核心机制，几十行伪代码就能说清：

```typescript
let currentEffect: (() => void) | null = null;

function createSignal(value: number) {
  const subscribers = new Set<() => void>();      // 订阅者图
  const read = () => {                            // 【读时追踪】
    if (currentEffect) subscribers.add(currentEffect);
    return value;
  };
  const write = (next: number) => {               // 【写时通知】
    value = next;
    for (const fn of subscribers) fn();           // 精确遍历订阅者
  };
  return [read, write];
}

function createEffect(fn: () => void) {           // "声明 UI 依赖谁"
  currentEffect = fn; fn(); currentEffect = null; // 首跑即完成收集
}
```

- **读时追踪**：effect 执行期间，任何被读到的信号都会把它记进自己的订阅者集合（getter 里干的事）
- **写时通知**：信号被赋值时，遍历订阅者集合逐个重跑（setter 里干的事）

把信号看作节点、订阅关系看作边，就得到**信号依赖图**——所有 Signals 框架的心脏：

```
        ┌──────────┐  读   ┌────────────┐  读   ┌──────────────┐
 setA ─▶│ signal A ├──────▶│ computed C │──────▶│ effect: DOM  │
        └──────────┘       │  = A + B   │       │ "Count: {C}" │
        ┌──────────┐  读   └─────▲──────┘       └──────────────┘
 setB ─▶│ signal B ├─────────────┘
        └──────────┘

 setA(2) ─▶ 标记 C 脏 ─▶ C 重算 ─▶ 只重跑读取了 C 的 effect ─▶ 精确改一个 textContent
```

Vue 的 Proxy、Solid 的 signal、Angular 的 signal，底层都是这张图，只是"追踪"的植入方式不同（Proxy 劫持 vs 显式函数调用 vs 编译器插桩）。

## 4. 四大流派对比（React / Vue / Svelte / Signals）

| 流派 | 核心机制 | 更新粒度 | 优点 | 缺点 |
|---|---|---|---|---|
| React | 不可变 + vdom + 组件重跑 | 组件级（diff 后落到 DOM） | 心智简单、不可变快照、生态最大 | 无关代码重跑、diff 有成本、memo/useMemo 补丁学不完 |
| Vue | Proxy 劫持 + 依赖收集 | 组件级（引用级追踪） | mutable 写法自然、模板静态提升 | 组件内重跑、深层响应式有代理开销 |
| Svelte | 编译时响应式（runes） | 编译定向更新 | 运行时极小、产物小 | 响应性依赖编译器（非纯 JS 语义）、5.x 前有 `$:` 陷阱 |
| Signals | 值 + 订阅者图，读收写通知 | 表达式/绑定级 | 组件只跑一次、无 diff、可脱离 UI 用 | 拓扑结构对新手不透明、需防循环依赖 |

### React：setState → re-render → diff

```tsx
function Counter() {
  const [count, setCount] = useState(0);        // 不可变：每次换新引用
  return <div onClick={() => setCount(count + 1)}>Count: {count}</div>;
} // setCount → 整个 Counter 重跑 → 新旧 vdom diff → 打补丁到 DOM
```

当组件变大、状态变多，无关重跑的浪费就得靠人工补丁挡：

```tsx
const ExpensiveList = React.memo(function ExpensiveList(props) {
  /* 不重跑的条件：props 浅比较相等 */
});
const double = useMemo(() => count * 2, [count]);  // 手动声明依赖
const inc = useCallback(() => setCount(c => c + 1), []); // 手动固定引用
// 这些 API 本质是"手动版的依赖追踪"——Signals 派的口头禅：
// "你的 memo/useMemo，就是我们编译器/运行时自动做的事"
```

### Vue：Proxy 劫持 + 依赖收集

```typescript
const state = reactive({ count: 0 });           // Proxy 包一层
// 模板编译成 render 函数，effect 内跑 render：
// render 读 state.count → getter 记下"这个组件依赖 count"
state.count = 1;  // setter 拦截 → 通知订阅的组件 effect → 重跑整个 render → patch
```

Vue 已经是推模型（Proxy 里就是第 3 节的读写钩子），只是订阅单位是**组件的 render effect**，所以更新粒度停在组件级；`shallowRef`/`ref` + `computed` 则是向 Signals 收敛的形态。

### Svelte：编译时响应式

```svelte
<script>
  let count = $state(0);            // Svelte 5 runes：编译器识别 $state
  const double = $derived(count * 2);
</script>
<button onclick={() => count++}>{count}</button>  <!-- 编译成定向赋值代码 -->
```

`$:`（Svelte 4）与 `$state/$derived`（Svelte 5）会被编译器分析出依赖关系，**直接生成"改谁、更新哪个 DOM 节点"的定向代码**，运行时几乎不需要通用依赖追踪。代价：响应性规则是编译器魔法，不是纯 JS 语义（普通函数返回值就丢响应性）。Svelte 5 的 runes 本质上是把信号语义搬进了编译器+轻量运行时——也是收敛证据。

### Signals（Solid / Angular / Preact / Qwik / Vue ref）

```tsx
const [count, setCount] = createSignal(0);
const double = createMemo(() => count() * 2);

createEffect(() => {
  div.textContent = `Count: ${count()}`;        // 只这一行订阅了 count
});
setCount(1);  // → 只重跑上面这一个 effect，组件函数不再执行
```

信号 = **值 + 订阅者集合**。组件函数只是一次性的"装配代码"：跑一次，把 DOM 绑定/表达式注册成图中的节点，之后图自己流动。JSX 只是"看起来像 React"的语法，语义完全不同。

这一派的共同点远大于差异——Solid 的 `createSignal`、Angular 的 `signal()`、Preact 的 `signal()`、Qwik 的 `useSignal`、Vue 的 `ref`，API 形态几乎一致（读值/写值/派生 memo/副作用 effect），因为它们实现的是同一张第 3 节的图，差异只在编译器配合程度（Solid 最深：JSX 表达式被编译成直接的图节点）与默认追踪深度（Vue deep vs Solid 显式）。

## 5. 为什么 Signals 是收敛方向

各框架十年殊途同归，都在往"读时追踪、写时通知的细粒度图"靠：

- **Vue 3**（2020）：`ref`/`computed`/`effect` 就是一套信号实现，Vue 3.5 进一步优化响应式传播
- **Angular 16**（2023）：放弃 Zone.js 全局脏检查，引入 `signal()`/`computed()`/`effect()`
- **Preact**（2021–）：`@preact/signals` 作为官方状态方案，"组件零重跑"
- **Solid/Qwik**：信号原生派，Qwik 甚至把信号序列化到 HTML 里做恢复
- **Svelte 5**（2024）：`$:` 转向 runes `$state/$derived`——编译时魔法让位于运行时信号语义
- **React 生态**：React 核心坚持拉模型，但 `useSyncExternalStore`（2022）是官方为"外部存储订阅"开的口子；jotai（原子=信号）/valtio（Proxy 通知）/zustand 订阅模型，全是库作者在不改 React 内核的前提下"补"信号语义

判断依据很简单：**拉模型靠"重跑+diff"保证正确性，代价随组件树规模线性涨；推模型靠"精确订阅"跳过无关计算，代价只是建图。** 当 memo/useMemo/useCallback/selector 这些补丁越打越多时，说明框架在用人工方式重建订阅图——那就直接用带图的模型。

## 6. 细粒度的含义

"细粒度（fine-grained）"不是"更快"的玄学形容词，有精确含义：**依赖追踪的最小单位是"哪个表达式读了哪个信号"，而不是"哪个组件读了哪些状态"。**

```tsx
// Solid：组件跑一次，产生两个独立订阅
function App() {
  const [count, setCount] = createSignal(0);
  const [name, setName] = createSignal("opencode");
  return (
    <>
      <div>Count: {count()}</div>      // 订阅点 A：只依赖 count
      <div>Name: {name()}</div>        // 订阅点 B：只依赖 name
    </>
  );
}
setCount(1);  // 只有订阅点 A 重跑，B 碰都不碰；组件函数更不会重跑
```

对比 React：`setCount` 会重跑整个 `App`，`Name` 分支也被重新求值（哪怕结果一样），再靠 diff 丢弃。对比 Vue：整个组件 render effect 重跑，再 patch。用表汇总一次：

| 模型 | setCount(1) 时发生什么 | Name 分支被重算？ | diff？ |
|---|---|---|---|
| React | `App` 重跑 → vdom diff → patch | 是（重算后丢弃） | 有 |
| Vue | App 的 render effect 重跑 → patch | 是（重算后丢弃） | 有（模板级） |
| Solid | 仅订阅点 A 的表达式重跑 | 否 | 无 |

粒度层级：**组件级（React/Vue） → 绑定/表达式级（Signals/Svelte）**。粒度每细一级，"白算后丢弃"的部分就少一截、diff/patch 的工作量就小一截——这是 Solid 性能的直接来源，而不是什么神秘优化。

## 7. opencode 为何受益（SSE 高频事件投影）

opencode 四端（TUI/Web/桌面/服务端共享层）选 SolidJS，除了"一套组件语言渲染到 DOM 和终端"（见 [2_solidjs.md](2_solidjs.md)），现实动机是**事件流频率**：

- LLM 流式回复时，SSE 每秒推几十上百个 `text.delta`，`packages/client/src/solid/data.ts` 的 `createData()` 把它们投影进响应式 store——每个 delta 只触碰"那条消息的 text"这一个节点
- 细粒度订阅意味着：**只有真正读取该消息文本的组件**（当前会话的消息气泡 / TUI 里可见的那几行）会重算；会话列表、输入框、其他消息的组件全部纹丝不动
- TUI 端尤其受益：终端整屏重绘有 60FPS 预算，OpenTUI 渲染器收到的是"某行变了改某行"的精确更新，而不是每次 delta 触发全树 re-render 再 diff 出"其实只有一行变了"——高频流式场景下，这个差别就是流畅与掉帧的差别

一句话：**事件流越密，"只更新真正依赖它的那一小块"的价值越大**——这正是细粒度响应式的卖点在 opencode 里的具象化。
